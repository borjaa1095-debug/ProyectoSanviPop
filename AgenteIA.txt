Comparación de mi proyecto con el proyecto desarrollado con Codex
Los dos proyectos parten de las plantillas de SanviPop y utilizan los mismos servicios, pero organizan el código de forma diferente. En mi proyecto, las peticiones se separan en clases como AuthService, ProductsService, UsersService y RatingsService. Esto permite localizar las operaciones de cada apartado sin mezclarlas con el código de la página. El proyecto desarrollado con Codex reúne muchas funciones compartidas en common.ts, como las peticiones, el manejo de la sesión y varias utilidades para mostrar datos.
Una diferencia concreta está en las valoraciones. Mi proyecto utiliza una función compartida para crear las tarjetas, mientras que el proyecto de Codex clona un template HTML y rellena sus elementos. Además, Codex solicita los datos del usuario y sus valoraciones en paralelo con Promise.all; en mi proyecto primero se obtiene el usuario y después sus valoraciones. Ambas soluciones separan la consulta de datos de su presentación, aunque lo hacen de distinta manera.
También cambia la forma de informar al usuario. Mi proyecto utiliza principalmente alertas para comunicar algunas operaciones y errores, mientras que el de Codex muestra más mensajes dentro de la propia página. En las valoraciones, mi versión presenta los textos en español y adapta la media al formato español; la otra utiliza textos en inglés y calcula su presentación con toFixed.
AGENTS.md recoge las normas de estructura, estilo y comprobación de mi proyecto. Se creó después de ratings.html, por lo que no influyó en la implementación inicial de esa página. Durante la creación del proyecto con Codex hubo un problema de conexión con la API que se solucionó tras volver a revisar los archivos. Esto muestra que generar el código no sustituye la necesidad de probar las peticiones y comprobar el comportamiento de las páginas.
Al comparar los dos, mi proyecto mantiene una separación más clara por clases de servicios, mientras que el de Codex concentra más utilidades y reduce algunas repeticiones mediante funciones compartidas. Las dos formas tienen ventajas: las clases facilitan encontrar las operaciones de cada recurso y las funciones comunes permiten reutilizar tareas entre páginas. La comparación me ha servido para entender que una misma aplicación puede organizarse de distintas maneras y que hay que valorar tanto la estructura como su funcionamiento.
